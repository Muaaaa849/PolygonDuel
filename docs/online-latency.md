# オンラインの入力・反撃・通信遅延の調査（2026-10-11）

調査元: `ed7c2f4`。60Hz、入力遅延1〜3F、巻き戻し上限8F。

## 確認した問題と修正

### 通信待ち中にタップを消費していた

`battle.ts` は `readLocal()` を先に実行し、その後 `RollbackSession.tick()` が
通信待ち・時間合わせで進行を断っても、タッチのラッチとキーボードの押下記録を消していた。
待ち時間中に押して離すと、その入力がシミュレーションに一度も届かない。

`tick()` に遅延評価する入力コールバックを追加した。画面側は採用されるtickでだけ入力を
読み、記録を消費する。先に巻き戻しも適用するため、エイム可否なども修正後の状態で判断する。
既存の数値入力APIは決定論テスト用に維持。実UIは必ずコールバックを使う。

### 入力遅延が反撃の受付を削っていた

速いGCは、ガード成立後1〜10Fに新しく攻撃を押すと予約され、ガード硬直終了後に発生10Fで出る。
11F以降に押すと発生14Fの通常GCになる。10Fにはヒットストップも含む。
旧実装は入力を適用したフレームで判定するため、遅延3Fでは実際の受付が7Fになっていた。

双方が開始時に合意した遅延を `GameState.gcInputDelay` に保存し、判定を
`入力適用フレーム - ガード成立フレーム - 合意した遅延` に変更した。
この値はスナップショット・チェックサムに含まれ、ラウンドをまたいでも維持する。
CPU戦は0。自端末のRTTや描画時刻をシムに持ち込まない。
ガード成立以前／同フレームに押した入力は、後から届いてもGC予約にしない。

| 押した時刻 | 遅延3Fで旧実装 | 修正後 |
| --- | --- | --- |
| ガード後8F | 11F扱い、通常GCをガードされる | 8F扱い、速いGCが命中 |
| ガード後10F | 13F扱い、通常GCをガードされる | 10F扱い、速いGCが命中 |
| ガード後11F | 通常GC | 通常GC |

判定対象は、従来どおりGC可能なガード硬直中の新規押下。
技の発生・硬直・リーチ・押し戻しは変更しない。先端当てで届かない仕様や、
ヴォルトの突進をガードしても相手が+7Fというルールも維持する。
この補正は固定入力遅延を取り戻すもの。巻き戻しでガードの表示自体が遅れて現れた時間や、
画面描画・端末入力の遅延までは補償しない。

## 通信処理の改善

- **送信待ちの蓄積を制限**: DataChannel の `bufferedAmount` と今回のサイズの合計が512バイトを
  超えると古い入力パケットを追加しない。最大入力パケットは151バイト。
  次のパケットにも未確認入力が入るので、ブラウザ内に古いデータを際限なく積まず復旧できる。
  既にSCTPやOSに渡ったデータを取り消すものではなく、512バイトも時間上限ではない。
  `congestionDrops` でこの抑制回数を確認できる。
- **RTT計測を対戦用チャンネルへ**: 500msごとのping/pongを5バイトのバイナリにし、
  順序保証・再送なしの `game` チャンネルで測る。従来の信頼性あり `ctrl` では、
  再送待ちを含むRTTで入力遅延を決めてしまう可能性があった。中央値による平滑化は維持する。
- **受信済みフレームをすぐ利用**: 前の入力が欠けていても、そのフレーム自身の入力があれば
  予測値で代用しない。既に予測済みなら、欠けた前フレームの到着を待たず巻き戻す。
  確定フレームとチェックサムの条件は従来どおり連続受信を必要とする。
- **短い不正パケットの検査**: ヘッダー・入力個数分の長さを確認してから読み、受信処理の例外を防ぐ。

## 回線経路の調査と判断

- GitHub Pages はファイル配信。対戦入力をGitHubへ往復させる構成ではない。
- PeerJSのルームサーバーは接続交渉だけで、P2P接続後に閉じる。これを移転しても対戦RTTは下がらない。
- STUNも接続候補を得るためのもので、通常の対戦パケットを中継しない。
- 直接接続できないリンク部屋は、`eu-0.turn.peerjs.com` / `us-0.turn.peerjs.com` の
  公開TURNへフォールバックし得る。日本などから利用する場合、遠い地域を経由することが
  大きな遅延の要因になり得る。ただし今回の環境から、ユーザーの選択経路や実RTTは測れない。
- 次のインフラ対策は、実対戦で「中継」になっていることとRTTを確認した上で、利用地域に近い
  TURNまたは地域分散TURNを用意すること。ブラウザへ長期管理トークンを埋め込まず、
  短期認証情報を発行する仕組みが必要。今回は新しい外部サービスや費用の発生する契約は追加していない。
- TURNを単純に削除すると接続できない回線が増える。常時TURNへ固定すると直結より遅くなる
  可能性があるため、どちらも採用しない。
- 入力パケットは通常毎秒60回、最大でもペイロード約9.1KB/s/方向。周波数や再送量を増やしても
  距離・混雑による遅延は消えず、送信待ちを増やし得るため増やさない。
- 遅延を常時0Fにすると巻き戻しが増える。対戦途中の自動変更には双方のフレーム合意と
  入力の重複・欠落防止が必要。今回の修正では1〜3Fを開始時に決め、対戦中は固定する。
- 端末の描画停止も相手の通信待ちを起こす。ソフトウェア描画のテスト環境での停止数を、
  実機の回線性能やインターネットRTTの改善量とは扱わない。

## 検証

全508テスト・型チェック・ビルドが通過。Chromiumのキーボード／タッチ両モードで、
通信待ち中の短い押下が再開後に反映され、双方のチェックサム照合で同期ずれ0件を確認した。

- `tests/online-input.test.ts`: 通信待ち・時間合わせ中の入力保持、エイム情報、巻き戻し後の
  入力取得、順序入れ替わり、不完全パケット、2台分の遅延0〜3F・片道0/3/6F、
  ジッター0〜3Fと約9%ロスを加えた確定反撃と同期。
- `tests/guard-counter.test.ts`: 全10キャラの攻防の組み合わせで、遅延1〜3Fを補正しても
  近距離の通常1段目止めに速いGCが確定する。既存の方向・距離・連打・保持入力のテストも維持。
- `tests/transport.test.ts`: 対戦用ping/pong、重複応答、ping欠落、送信待ち上限、復旧、閉じたチャンネル。
  500msの送信待ちと復旧後毎tick 1パケットの排出をモデル化し、上限なしより進行が回復することも比較する。
- 既存の全体テスト、型チェック、ビルド、処理時間の予算テストを実施。
- `tools/online-test.mjs`: Chromiumを2つ接続し、実際の対戦画面で相手を一時停止してから
  押して離し、再開後の攻撃発生を確認する。`TOUCH=1` はタッチ操作、指定なしはキーボード。
  その後も対戦し、チェックサム照合あり・同期ずれ0をassertする。

実機のiPhone/Android間、携帯回線間、遠距離TURN経由での比較は未実施。
確認したのはゲーム側の不具合解消と検証条件下の同期であり、インターネットのRTTが
何ms下がるという実測結果ではない。
